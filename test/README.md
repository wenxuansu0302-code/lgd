# LGD 隧道验证模拟前端

本地地址：**http://127.0.0.1:8090**。预留原 LAN 地址：**http://192.168.0.100:8090**。

本次按用户选择，先使用 **COM5 读取 GW2、COM8 读取核心、SSH 读取服务器**。前端独立于三端业务，不修改本机网卡或三端业务代码。GitHub 仓库中的目录为 **`test/`**，本地开发目录为 `tunnel-demo-frontend/`。前端没有把 192.168.0.100 自动配置到断开的网卡；后续接上 LAN 并配置该地址后，同一个程序即可使用原 IP 访问。

## 如何判定构建成功

| 层次 | 成功判据 | 前端证据 |
|---|---|---|
| 进程及网络准备 | 三端所需服务运行，10.78 承载地址和 10.77 业务 VPN 地址正确 | 三端服务状态、PID、重启计数及真实网卡地址 |
| 业务通路 | GW2 从自身 VPN 地址访问核心 11500，收到匹配随机 nonce 的协议 ACK，核心监听正常，组处于启用状态 | 实际探测结果、RTT、核心接收计数；与单纯 ping 不同 |
| 关键 JSON 可靠传输 | 同一 delivery ID 发两次，收到 accepted/duplicate，独立核心接收实例只发布一次 | “运行隔离数据验收”结果及报告中的发布次数、重复次数 |
| 图片及身份检查 | 完整 JPEG 的发送、接收 SHA-256 一致；错误网关身份被拒绝 | 测试图像、198,749 字节长度、哈希、身份拒绝证据 |
| 管理链路持续运行 | GW2 遥测持续更新，而不只是隧道仍可探测 | 核心 10017 遥测年龄，超过有效期明确提示陈旧 |
| 故障恢复 | 维护窗口内的真实业务退出、承载中断后恢复，且恢复行为符合设计 | 实测前后 PID、队列及恢复时间；离线演示不算通过 |

**前四项通过可确认当前软件通路和独立数据传输有效；不能据此宣布全部系统定型。** 管理遥测、故障恢复、持续摄像头负载、断电启动与实物短波/卫星仍应分别验收。此次读取已发现管理遥测陈旧，页面保留这一实际问题，不用成功探测来掩盖它。

## 启动与使用

1. 保持三端现有 `lgd.target` 运行。将边缘接 COM5、核心接 COM8，并关闭占用这两个串口的终端工具。两个串口需已有 root 登录提示符；后端不保存登录密码。
2. 在本机双击 `start.cmd`，或执行 `powershell -NoProfile -ExecutionPolicy Bypass -File start.ps1`。需要 Python 3.9+、Windows PowerShell 和 OpenSSH 客户端，页面无 npm 安装或构建依赖。服务器使用已配置的 SSH 密钥登录 `root@47.99.47.169:54430`。
3. 打开 http://127.0.0.1:8090。默认“真实联调”，等待首次三端采样。约每 6 秒完成一轮采集（加上命令往返时间），页面共享缓存，多浏览器不会重复抢占串口。采样超过 22 秒、采集失败、错误地址等不会继续显示实时通过。
4. 点击“运行隔离数据验收”，阅读说明后开始。进度出现在验收按钮和时间线中，通常约 1 分钟。期间常规串口采样暂停；完成后恢复。
5. 检查 JSON 只发布一次、图片哈希一致、错误身份拒绝。点击“导出验证报告”，保存带时间戳的真实观测、结果与原始证据。
6. “离线演示”用于展示正常、隧道中断、组停用、恢复重试四种场景。演示有固定横幅，测试按钮不可用；导出报告也明确标注 demo，不与真实数据混用。

原 IP 联调时：将电脑有线网口设置为 `192.168.0.100/24`，连接核心 `fm1-mac2` 所在 LAN（核心为 `192.168.0.233`）。无须为这个设备 LAN 配置默认网关，也无须修改 WLAN 的 Internet 连接。若 Windows 防火墙阻止其他 LAN 设备访问，应仅允许可信设备 LAN 访问本程序的 8090/TCP。页面继续按当前串口方式采样；LAN 地址负责前端访问，不改变实际 5G/VPN 路由。

## 隔离数据验收如何工作

测试临时开放 Nebula 内的 11650/TCP，并仅授权既有边缘证书访问核心的独立测试接收器。独立接收器从已部署的 `gateway_v1.py` 导入真实接收类，建立独立 Hub 与测试 inbox；发送端从 `gateway_merged.py` 导入真实传输类。不会调用生产告警、短波呼叫或卫星发射，也不将测试 payload 写入生产传感器缓存。

流程为：准备固定图像 → 启动独立接收器 → 重发 64 KiB JSON → 发送 JPEG → 发送错误身份数据 → 对生产 11500 做无业务发布的探测 → 检查接收次数与 SHA-256 → 停止接收器并撤销临时访问规则。

正常结束或异常退出均清理两个设备；清理失败会使结果不通过。设备上另设置约 150 秒的自动清理计时器，电脑中途断开时仍能撤销临时放行，测试接收器本身也有限时。测试所需的 `/root/lgd_integrated_stage_20261013`、`/root/lgd_tunnel_stage_20261013/validation` 是独立测试目录，不是生产运行数据目录。

**生产计数与隔离验收计数分开显示。** 当前没有摄像头或传感器输入时，生产 JSON 和媒体计数可能仍为零，即使独立验收已成功。此页面不会把离线动画或静态测试图片当作真实视频输入。

## 故障恢复测试方法

在业务允许短暂停顿的维护窗口，记录页面原始 JSON 中的三端 PID，再选择一项实际故障进行测试，期间保存页面导出的前后报告：

| 场景 | 可执行的维护操作 | 预期效果 |
|---|---|---|
| 边缘业务异常退出 | 边缘终端执行 `systemctl kill --kill-who=main --signal=KILL gateway-startup-gw2.service` | 业务 PID 改变并恢复；拨号、OpenVPN、Nebula PID 不变 |
| 外层承载重连 | 边缘执行 `systemctl restart lgd-tcp-carrier.service` | 探测短暂失败后恢复；关键消息待确认数不应因重连被清空；视频暂停期间无需转入短波 |
| 服务器业务暂停 | 服务器执行 `systemctl kill --kill-who=main --signal=STOP lgd-server-v8.service`，随后必须以 `CONT` 恢复 | 边缘到核心业务探测应继续成功；管理服务暂停不能被误判为服务器健康 |
| 实际组停用 / 恢复 | 通过既有组控制接口停用、恢复 GW2 | 通路仍可探测；ACK 中 enabled 变化，停用期间业务被拒绝；界面区分“组停用”和“断链” |

前端没有自动触发这些故障的按钮，避免演示时误操作正在运行的业务。已有 2026-10-13 实测记录见 `release_v1.2_integrated/README.md`；本前端不会把那份历史记录当成本次新的故障测试。

## 文件结构

```text
test/                           # GitHub 目录；本地开发目录为 tunnel-demo-frontend
├── server.py                    # 本机后台：串口/SSH采集、缓存、测试编排、HTTP页面/API
├── start.cmd / start.ps1         # 启动，识别已有实例并避免重复占用串口
├── stop.ps1                     # 仅停止本机演示服务，不停止三端业务；验收中禁止停止
├── README.md
├── dist/
│   ├── index.html               # 页面结构与确认对话框
│   ├── styles.css               # 桌面与窄屏布局
│   ├── app.mjs                  # UI交互、真实/演示切换、图表、报告导出
│   ├── model.mjs                # 有效期、成功判据与离线场景模型
│   └── validation.jpg           # 固定隔离传输测试样本
├── ops/
│   ├── serial_exec.ps1          # 115200 8N1 串口命令封装，退出释放串口
│   ├── collect_node.py          # Linux端只读采样与无业务探测
│   ├── setup_network_validation.py
│   ├── start_validation_receiver.py
│   ├── validation_sender.py
│   └── finish_network_validation.py
├── tests/                       # 判据、异常清理和动作接口测试
└── .runtime/                    # 本机临时缓存、PID、日志、验收报告；不进入发布包
```

停止本机前端：`powershell -NoProfile -ExecutionPolicy Bypass -File stop.ps1`。运行时 stdout/stderr 位于 `.runtime/server.log`、`.runtime/server-error.log`，最新数据验收结果在 `.runtime/last_validation.json`。
